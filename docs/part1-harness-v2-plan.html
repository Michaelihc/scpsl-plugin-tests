1 · Context & goals

The current harness (.tests\Behavioral) is synchronous, teleport-only, and pushed every real test into ad-hoc auto-run verifier plugins. Consequences observed in the field: dummies spawned mid-air at y=1000, tests passing on server-visible state while real players fell into the void, waits faked with premature Pass() + deferred log lines.

Part 1 rebuilds the harness greenfield — new folder, new assembly, no code reuse from the old harness, old style only where it earned it (the raycast/settle probe patterns proven in existing plugin verifier code are lifted as ideas, rewritten clean). The old harness stays untouched and deployed wherever it is; nothing breaks.

The pattern being automated is the owner's manual playtest loop: spawn in, teleport to the feature under test (not walk the whole facility), walk around locally, try abilities/items, shoot a few dummies, watch what happens. Teleports are a legitimate tool — the failure mode was never "a TP happened", it was unvalidated TPs (mid-air, into void, inside geometry) treated as safe placement.

  • Coroutine-native scenarios — waiting, settling, and walking are first-class.
  • Three fidelity tiers — one scenario source runs at any supported tier.
  • Standard tier = scoped playtest — same gameplay rules as e2e; the only shortcuts are fast-travel (probe-validated TP) to the slice under test and pre-arranged state (start mid-objective). Everything inside the slice is native, native-speed, dummy-shots-for-damage.
  • EndToEnd tier = the whole path — native spawns only, all travel bot-walked (spike-verified BotOrders), zero shortcuts: the complete round-like path from spawn to objective.
  • Part 2 seams built in — orders-style actor API, JSONL telemetry, monitor interface, perception chokepoint identified. Part 2 plugs an AI/LLM brain into the same body.
Bot layer (separate track, will be rewritten): the owner plans to rewrite the bot plugin, so part 1 must not couple to it. The harness defines its own minimal IMovementProvider seam; the current spike BotOrders is just the first pluggable provider behind it. Blocked-edge replanning / clutter recovery stay in the bot track (toy-in-doorway repro is its acceptance test). Part 1 treats a stalled walk as a loud scenario failure, never a hang.

Core contracts (sketch — implementer refines)

public enum Fidelity { Quick, Standard, EndToEnd }        // runner picks one per run

public abstract class Scenario {
  abstract string Name;  virtual string[] Aliases;  abstract string Description;
  abstract FidelityRange Supported;                       // e.g. Standard..EndToEnd
  virtual float TimeoutSeconds => tier-scaled default;
  abstract IEnumerator<float> Run(ScenarioContext ctx);   // MEC coroutine — real waits
}

// ScenarioContext — what a scenario touches
ctx.Fidelity                          // the tier this run executes at
ctx.SpawnActor(label, role, SpawnSpec)  // SpawnSpec: NativeRole | At(pos) — At forbidden at EndToEnd
ctx.Require(cond, msg)  ctx.Info(msg)  ctx.Emit(evt)      // telemetry
ctx.Wait(s)  ctx.WaitUntil(pred, timeout)
ctx.Pass() / fail via RequireException                    // result set ON COMPLETION, never early

// Actor — fidelity-adaptive verbs (orders API; part 2 reuses these verbs)
actor.GoTo(Vector3 | RoomName)        // travel to an objective:
                                      // Quick: raw TP · Standard: VALIDATED TP (probe target first:
                                      //   ground within drop, in-bounds, capsule not in geometry → TP → Settle;
                                      //   invalid target = loud FAIL, exactly the mid-air-spawn bug class)
                                      // EndToEnd: walk via IMovementProvider; stall/off-mesh/timeout ⇒ loud FAIL
actor.WalkTo(Vector3 | RoomName)      // local movement AT the objective — walked for real at
                                      // Standard+ (playtest realism); Quick may TP
actor.LookAt(target)  actor.GiveItem(t)  actor.UseHeldItem()  actor.Attack(victim)
                                      // Standard+: these are NATIVE and take native time —
                                      //   UseHeldItem on a 20 s-charge item spends the 20 s;
                                      //   Attack = actually aim + fire at the dummy, no stat pokes
                                      // BATTERIES-INCLUDED CONTRACT: aim alignment (camera pitch/yaw
                                      //   to hitbox, lead, weapon ready/reload state, melee range approach,
                                      //   fire-until-hit-confirmed w/ timeout) is implemented ONCE inside
                                      //   the verb. Scenarios NEVER hand-roll rotation/aim/fire mechanics —
                                      //   a scenario that needs Quaternion math means a missing verb:
                                      //   add the verb to the harness, don't inline it.
actor.Settle(maxDrop)                 // wait grounded ≤ N s, assert no fall/void
actor.Soak(seconds)                   // leave alone; bounds+ground monitored throughout
actor.Damage(...)                     // Quick ONLY (setup/smoke plumbing); Standard+ throws —
                                      //   damage happens by shooting dummies, nothing else

Tier semantics

Governing principle: Standard and EndToEnd play by identical gameplay rules — every action native, every action at native speed, damage only by real shots at dummies. They differ in scope-thinking, not in what ops are allowed. Standard verifies a slice: fast-travel to it, optionally start with the objective partially completed. EndToEnd verifies the whole path: native spawn to finish, no shortcuts of any kind. Quick is the only tier where non-native shortcuts exist at all.

Movement provider (swappable seam — bot rewrite planned)

The harness owns a minimal IMovementProvider (roughly: bool Available, OrderWalk(hub, target), Status(hub) → moving/arrived/stalled/off-mesh + reason, Cancel(hub)). BotOrdersProvider implements it by binding to the spike's SCPSLBot.AI.BotOrders via reflection at startup — no compile-time reference, so the planned bot-plugin rewrite only has to ship a provider (or matching surface) later; harness code and every scenario stay untouched. No provider on the port ⇒ walk-requiring runs are skipped with an explicit SKIP result, never a crash or silent pass.
